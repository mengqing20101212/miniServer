# RPC 等待与失败补发

## 普通调用

通用 Server2Server RPC 和 Gate→Game 同步转发使用同一套 Future 等待表。
先登记 callId 和预期响应 CMD，再发送，覆盖快速回包；响应直接完成对应 Future，不再每 10ms 扫描和解析接收队列。
单连接最多 256 个等待项，进程最多 8192 个；超时、取消、断线和关闭释放等待项。
RPC 连接上的迟到响应直接丢弃，不累积到普通收包队列。机器人等普通 NetClient 的收包队列行为保留。

异步调用 `RpcUtils.asyncRequest` 不再占用 common pool 执行同步轮询；连接解析在虚拟线程中进行。
异步结果以异常表达 TIMEOUT、TRANSPORT、BUSY、CLOSED、PROTOCOL 等原因。
旧同步接口仍保留失败返回 null 的兼容行为，日志记录具体原因；Netty IO 线程禁止同步等待。
普通 Future 的非 async 回调可能运行在响应线程，业务回调应使用自己的执行器，不能阻塞网络线程。
玩家与场景已有的所属队列和执行顺序保留。本次不引入新的业务线程池。

## 只有失败才写 RocksDB

正常成功调用不产生 RPC outbox 磁盘 IO。首次发送失败后，先记录 requestId/callId、目标、CMD、原因，再同步写 WAL。
`NONE` 不保存；`SEND_FAILED_ONLY` 保存网络不可用/写出失败；`SEND_FAILED_OR_TIMEOUT` 也保存超时。
超时和断线都不等于远端业务没执行，所有允许补发的修改接口必须具备业务幂等能力。
Gate 普通业务转发默认只保存发送失败，不再默认保存所有业务的响应超时。
失败到持久化之间的崩溃窗口按当前需求不另做保障；持久化失败会明确打印 `RPC FAILURE NOT PERSISTED`。
异步调用的失败持久化在虚拟线程中执行，不让网络或超时调度线程执行磁盘 IO。
旧同步调用返回失败前，会等待相应的失败保存尝试结束。

RPC 命令独立保存在 `rpc-outbox` RocksDB 中，复用已有 Fury 和 RocksDB 依赖，不能按实体主键合并命令。
首次与补发保持原 callId，补发包的连接 seq/sid 重建。
补发与新请求之间不提供全局业务顺序，依赖顺序的业务仍需版本校验或业务状态机。
启动恢复、周期扫描与节点上线共用单目标补发互斥，最多同时处理 8 个目标。
失败使用指数退避（5 秒至 8 小时），不再因 20 次重试或 72 小时到期删除。
补发先登记 Future，收到 callId、外层 CMD、内层响应 CMD 都匹配的响应才删除记录。
已确认业务完成后，Gate 的本地回包转发失败只记录通知失败，不因此再次执行远端业务。
没有确认协议或有效 callId 的原始单向消息留盘报警，不能仅凭网络写出成功就删除。

调用方选择补发策略，即声明接口支持幂等；框架尚未提供接收方跨重启的通用业务去重事务。
稳定 callId 是业务去重依据，不是“恰好执行一次”的保证，也不把旧的非幂等接口自动变为安全接口。

## 数据目录与旧 Redis 消息

默认目录：`${db.rocksPath}/${环境}/${serverId}/rpc-outbox`，使用持久磁盘。
`-Dminiserver.rocksPath=...` 同时影响实体和 RPC 存储根目录；也可用
`-Dminiserver.rpc.rocksPath=...` 单独配置 RPC 根目录。单目录只允许一个进程打开。
初始化在节点对外发布前执行，无法打开则启动失败。停止服务保留所有尚未确认的记录。
运行期补发不依赖 Redis；项目其他模块的 Redis 用法没有改变。

旧版 Redis 中的 `rpc:reliable:环境:发送方:目标方` 队列不会被新版本自动消费或删除。
升级前先由旧版本排空，或使用 `ReliableRpcStore.importLegacyRedis(target)` 显式迁移指定目标队列。
迁移逐条同步写入 RocksDB 成功后才移除对应 Redis 记录，失败立即停止并保留剩余消息。
迁移时停止该发送方的旧实例和补发任务；目标节点可以离线。重复迁移保留原 msgId，避免创建新命令。
没有确认协议的旧记录仍会留盘报警，需人工判断。

## 验证

`cd server && bash ./mvnw -B test`（Java 25）。新增测试使用真实本地 RocksDB 和内存网络适配器，
验证重启恢复、独立命令、原 callId、回包校验、快速响应、容量释放、迟到响应、断线及并发补发互斥。
这些测试不代表已经完成真实多机网络压测。
