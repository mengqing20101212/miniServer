## 一、可靠 RPC 补发 callId 机制

### 问题

GateServer 重启后会补发 Redis 中保存的可靠消息到 GameServer，但原代码用 `innerSeq + 1` 匹配响应包，
而响应包用的是外层 RPC seq，导致永远匹配不上，消息永远超时，永远不会被清理。

### 解决方案

引入 `callId` 机制：每次补发生成唯一 callId，Gate 侧等待响应时按 callId 匹配。

### 改动文件

**proto/Server.proto**
- `csGate2GameRpcGameCall` 增加 `int64 callId = 6`
- `scGate2GameRpcGameCall` 增加 `int64 callId = 5`

**server/core/.../rpc/ReliableRpcStore.java**
- `replay()`: 补发时生成 callId (`System.nanoTime() ^ Thread.currentThread().threadId()`)
- `buildReplayPacket()`: 将 callId 写入 csGate2GameRpcGameCall
- `waitAndHandleReplayResponse()`: 按 callId 匹配响应（不再用 seq）
- 移除了临时的 force reset 退避代码

**server/core/.../net/NetClient.java**
- 新增 `getReceiveMsgByCallId(long callId, int cmd)`: 按 callId 查找响应包
- 新增 `putBackPacket(AbstractMessagePacket)`: 匹配失败时放回队列

**server/GameServer/.../player/Gate2GameRpcGameCallController.java**
- 提取 callId，设置到 `player.getGamePlayer().setLastCallId(callId)`

**server/GameServer/.../player/Player.java**
- `sendMsg()`: 委托给 `gamePlayer.sendMsg()`（重构后）
- `sendErrorCode()`: 委托给 `gamePlayer.sendErrorCode()`（重构后）

**server/GameServer/.../net/GamePlayer.java**
- 新增 `lastCallId` 字段，getter/setter
- `sendMsg(cmd, message)`: 根据 lastClientCmd/lastCallId 决定封装方式
- `sendErrorCode(cmd, errorCode)`: 构建 scErrorCode 后调用 sendMsg
- `clearRequestContext()`: 清理 lastCallId 等状态

**server/GameServer/.../login/LoginManager.java**
- 创建 GamePlayer 时添加 `gamePlayer.bindPlayer(player)`（之前缺失导致 tick 线程 gamePlayer 为 null）

**server/proto/.../ProtoMessageFactory.java**
- 补充 CS_HeroAdd/SC_HeroAdd/CS_HeroLevelUp/SC_HeroLevelUp/CS_HeroStarUp/SC_HeroStarUp 分支

## 二、Move 移动协议

### 协议定义

**proto/Move.proto**
```protobuf
message csMove {
  int32 target_x = 1;
  int32 target_y = 2;
}

message scMove {
  ErrorCode result = 1;
  int32 current_x = 2;
  int32 current_y = 3;
}
```

**proto/Cmd.proto**
```
CS_Move = 1011;  // 移动请求
SC_Move = 1012;  // 移动响应
```

命名规范：message 小写开头 (`csMove`/`scMove`)，enum 大写 (`CS_Move`/`SC_Move`)

### 改动文件

**server/GameServer/.../move/MoveController.java** (新增)
- 注册 `CS_Move` handler
- `handleMove()`: 接收 csMove → 更新内存坐标 → 返回 scMove

**server/GameServer/.../GameServer.java**
- 注册 `new MoveController()`

**server/proto/.../ProtoMessageFactory.java**
- 添加 `CS_Move_VALUE → Move.csMove.parseFrom(data)`
- 添加 `SC_Move_VALUE → Move.scMove.parseFrom(data)`

**server/BotServer/.../command/impl/MoveCommand.java**
- 使用 `session.createPacket()` 确保 guid 正确（之前手动创建 guid=0 导致 GameServer 找不到玩家）
- 使用 `csMove.newBuilder()` 构建请求

**server/BotServer/.../command/impl/HeartbeatCommand.java**
- 修复 NPE：`null protoData` → `new byte[0]`
- 使用 `session.createPacket()` 确保 guid 正确

### 验证结果

```
net.log:
  发送: cmd=1011, data=[8, 64, 16, 26]  → csMove targetX=64, targetY=26
  收到: cmd=1012, data=[16, 64, 24, 26] → scMove currentX=64, currentY=26
```

## 三、sendMsg/sendErrorCode 收敛

### 问题

`sendMsg()` 和 `sendErrorCode()` 的封装逻辑在 Player.java 里，代码冗长且重复。
Gate2GameRpcGameCallController 里还有一个 `sendErrorViaRpc()` 做类似的事。

### 解决方案

把封装逻辑收敛到 GamePlayer，Player 一行委托。

### 改动文件

**server/GameServer/.../net/GamePlayer.java**
- `sendMsg(int cmd, AbstractMessage message)`: 根据 lastClientCmd 决定封装方式
  - `lastClientCmd == 0`: 无请求上下文，直接发
  - `cmd == lastClientCmd + 1`: 请求对应的响应，封装到 scGate2GameRpcGameCall，清理 context
  - 其他: 主动推送，封装到 scGate2GameRpcGameCall（不消耗 seq）
- `sendErrorCode(int cmd, ErrorCode errorCode)`: 构建 scErrorCode 后调用 sendMsg

**server/GameServer/.../player/Player.java**
- `sendMsg(Cmd.CMD cmd, AbstractMessage message)` → `gamePlayer.sendMsg(cmd.getNumber(), message)`
- `sendErrorCode(Cmd.CMD cmd, ErrorCode errorCode)` → `gamePlayer.sendErrorCode(cmd.getNumber(), errorCode)`
- 移除 Server/MessagePacketFactory/AbstractMessagePacket import

**server/GameServer/.../player/Gate2GameRpcGameCallController.java**
- 移除 `sendErrorViaRpc()` 方法
- player 不存在时直接调用 `session.sendErrorMsg()` 或内联构建 scGate2GameRpcGameCall

- `cb27a1f` refactor: sendErrorCode 收敛到 GamePlayer
- `d784693` refactor: sendMsg/sendErrorCode 收敛到 GamePlayer
