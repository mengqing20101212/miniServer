# MiniServer 线上项目优化方向

## 一、当前约束

- 项目已稳定运行多年。
- 固定分区分服，玩家不会常规漂移到其他节点。
- WebSocket + JSON + 阿里云负载均衡目前无明显线上问题。
- 数据库异步落库方案暂不确定。
- 当前没有现成压测模块和机器人。

## 二、需要做：第一优先级

### 1. 建立观测和基线

- 协议耗时：P50、P95、P99。
- JSON 解析和序列化耗时。
- MyBatis SQL 耗时、慢 SQL。
- RPC 耗时、超时、失败率。
- 线程池活跃数、队列长度、拒绝次数。
- 数据库连接池使用率。
- GC、Full GC、堆内存。

### 2. RPC 外围增强，不改底层框架

- 统一 `RpcClientWrapper`。
- 增加连接超时和读取超时。
- 使用独立 RPC 线程池，避免阻塞协议线程。
- 增加请求 ID、调用日志和失败分类。
- 增加有限重试、熔断和降级。
- 关键接口增加幂等参数。

### 3. 玩家业务串行化：先做高风险操作

- 不为每个玩家创建真实线程。
- 同一玩家进入同一串行队列。
- 不同玩家继续并行处理。
- 优先覆盖扣费、发奖、领取、交易、结算等操作。
- 避免重复操作、状态覆盖和并发修改。

## 三、需要做：第二优先级

### 1. 渐进优化 String + JSON 热点

- 不做全项目一次性替换。
- 先定位高频协议和高耗时模块。
- 避免同一请求重复反序列化。
- 复用已解析对象。
- 减少整份 JSON 重建和无意义全量写入。
- 新增模块优先使用明确的 Java 对象。

### 2. RPC 结果的应用层异步化

- 底层同步 Thrift/Nifty 保持不变。
- 同步调用放入 RPC 专用线程池。
- RPC 完成后把结果投递回玩家队列。
- 同一玩家的关键 RPC 保证顺序。
- 非关键通知类 RPC 可以先异步化。
- 扣费、发奖、交易等操作仍需明确成功结果。

## 四、暂不做：保持线上稳定

- 不全面替换 String + JSON 内存模型。
- 不改固定分区分服和玩家路由。
- 不改 WebSocket 接入协议。
- 不改阿里云负载均衡配置。
- 不重写 Thrift/Nifty RPC 底层。
- 不直接把全项目改为异步落库。
- 不大范围重写登录、连接和分服机制。

## 五、待定：数据库持久化

- 先统计读写频率、慢 SQL 和重复写入。
- 区分关键数据和普通数据。
- 关键数据需要事务、幂等和可确认成功。
- 普通数据再评估批量保存或异步快照。
- 如果采用异步落库，需要版本号、顺序、重试和恢复机制。
- 方案候选：同步事务、异步快照、Outbox、可靠消息。

## 六、验证方式

- 先用日志和线程栈定位，不依赖完整压测。
- 人工重复测试关键协议。
- 观察数据库变慢时线程池是否堆积。
- 观察同一玩家快速操作是否出现乱序。
- 后续只做最小 WebSocket 回放工具。

## 七、推荐实施顺序

1. 监控和耗时统计。
2. RPC 超时、日志、幂等外围封装。
3. 高风险玩家操作串行化。
4. 优化热点 JSON 的重复解析和序列化。
5. 根据真实数据决定数据库方案。
6. 必要时补充最小 WebSocket 测试工具。
